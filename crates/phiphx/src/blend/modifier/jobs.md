A Subdivision at level 0 is disabled — Blender's own rule, `is_disabled` → `get_render_subsurf_level(..) == 0` — but Blender asks it of the *evaluated* modifier, after its drivers have written the level. `read` was approximating it with `(levels > 0)` on the file's saved value, so a modifier a driver raises to 2 was never built to raise. - [x] **`is_disabled` swept across every type** (batch 190, from `MOD_*.cc`). Translated: **Displace** — `(!texture && direction == MOD_DISP_DIR_RGB_XYZ) || strength == 0`, and since this reader is textureless the first branch is the direction alone, so an RGB→XYZ displace is now dropped instead of falling back to an axis; **Lattice** and **Armature** — `!object`, dropped one step before `apply` bailed on the missing matrix, which also stops `skin_sources` building a skin for a rig that is not there. **Array** has an `is_disabled` but it only rejects a placeholder `curve_ob`/`start_cap`/`end_cap` of the wrong type, none of which this reader reads, so it is never disabled here. - [x] **`clone_box` — a per-frame stack, Blender's own answer** (batch 192, from `ModifierTypeInfo.copy_data` / `BKE_modifier_copydata_generic`). The open question was how a frame gets its own driven settings when `BlendSkinSource` is shared behind an `Arc`: interior mutability, a clone, or a per-frame cache. Blender settles it — the depsgraph evaluates a **copy** of the object and the drivers write into that copy, never into the file's stack. So `BModifier::clone_box` on all nine types, and `BlendSkinSource::evaluate_driven(deformed, world, driven)` clones the tail, lands that frame's settings on the clone, re-asks `is_disabled`, and runs it. `driven` empty clones nothing, so the open path is unchanged. Blender's copy ends with *"Runtime fields are never to be preserved"*, so a clone starts with an empty cache — which is exactly right for `BSubsurf`'s topology tables, since a clone may be handed a different mesh

- [x] **Driven modifier settings written into the stack** (batch 188). Batch 174 read and measured them; nothing consumed them, and underneath that the stack was evaluated at 0.90 *before* a single action was read, so the values did not exist yet when the geometry was built. Fixed in Blender's own order — the animation and the drivers now run first and the geometry last (`scene/read.rs`), and `BlendFile::driven_modifiers` carries the frame's settings by object address so `modifier_stack` picks them up with no signature changed and both consumers get them free. `BModifier::set_driven` takes one setting, each type applying its own reader's guards (a driven Subdivision level takes the same cap a file's does). Measured on MODDRIVERS: 15 of the fixture's 16 drivers are live (one is deliberately muted), 13 land on a field with exactly Blender's values, and 2 — `Solidify.material_offset`, `Mirror.bisect_threshold` — report `false` because this reader has no field for them. `driven_tests.rs`
- [x] **The prefix before an Armature applied once, not twice** (`prefix.rs`, batch 184). `modifier_jobs`/`apply_eval_jobs` builds the whole stack and `skin_sources` re-applies the part before the Armature from the same vertices with the same modifiers — on FLORIS 28 of 32 armature meshes, 39 modifiers, 20.7 ms of the 39.8 ms the stack apply itself took. It is a drop box rather than a cache because the order differs by open: an eager open applies the stack first so it puts and `skin_sources` takes, a progressive open reads the rigs first so it goes the other way; the taker removes the entry, so a subdivided mesh is not held once its second reader has it. THYMUS **−22%**, FLORIS **−11%** (one binary, `PHIPHX_NOSHARE=1` flipped, interleaved best-of-3). Evaluated geometry byte-identical both ways over 310,559 vertices (`examples/dump_eval.rs`), `tests/progressive_open.rs` and `tests/skinner.rs` green
