## Todo

- [ ] **One texture per socket — the walk is a chain, not a tree.** `BProcFinder::at` (`procedural.rs:109`) walks reroute → one Color Ramp → one Math → texture, and **breaks on anything else**, so a Base Color driven by a Mix of two textures yields no procedural at all and the material falls back to `eval.rs`'s folded mean. This is the single biggest material gap and it is what the CW-POSES set is made of: pose 26 carries **377 Mix nodes** across 337 materials, and its richest material (`Material.129`) layers 17 Image Textures through 17 Mix nodes. It is independent of the missing texture files — those materials fold flat even when every image is present. Needs a small tree in `BlendProc` and a loop in `procedural.wgsl`, which today evaluates exactly one texture per slot

## Done

- [x] Musgrave texture (batch 198) — it IS a Noise, and Blender says so: the node was removed in 4.1 and `eNodeMusgrave_Type` kept in the header marked *"Deprecated Musgrave Texture. Keep for Versioning"*, value-for-value identical to `eNodeNoiseTexture_Type` (MULTIFRACTAL 0, FBM 1, HYBRID 2, RIDGED 3, HETERO 4). So it reads straight into `BlendProcKind::NoiseFac` and the existing kernel evaluates it with **no WGSL change**. Three differences, each measured off pose 26's own DNA rather than assumed: the roughness input is named `Dimension`, there is no Distortion input and only a `Fac` output, and `musgrave_type` is an `int` where Noise's `type` is a `uchar`. `normalize` is off — Musgrave never remapped to 0..1. **No fixture carries a Musgrave node**, so this is verified by measurement (field widths, socket names, enum identity) and not yet by a truth test; pose 26's 11 nodes are the first real check
- [x] `bNodeSocket.display_shape` (`socket.rs`): the `eNodeSocketDisplayShape` a socket is DRAWN as — all nine, read as the DNA's own width, circle for a file too old to carry the member. A different question from `type`, which is what colours it. phiber paints all nine (`canvas/node/paint/shape.rs`)
- [x] **An area light's energy through the renderer** (batch 175; found in batch 173). `BlendLightData::energy` holds the file's stored value — 4/π of the UI watts for an area light — and `view3d/rendered/lamp.rs` passed it straight to a kernel that wants watts (`phiray/tests/lamp_power.rs` fed it 100 W by hand and matched Cycles). Settled with a Cycles render of a file (`fixtures/AREALIGHT.blend`, `truth/blender_area_light.py`): Cycles **1.861612**, ours **2.430 — 31% too bright**. The record now divides by `AREA_ENERGY_SCALE`, the same constant the driver pass multiplies by, so the field keeps meaning the stored value on both sides of the boundary; after it, **1.908** against Cycles' 1.862 — the same 2.5% the hand-fed lamp carries (`phiber/tests/a_files_area_light_reaches_the_kernel_at_its_watts.rs`, `rendering.md` §71). Point, spot and sun store the watts — the irradiance, for a sun — directly and take no conversion
- [x] World drivers (`world_driver.rs`): `World.adt` for its own `color` (hard 0..∞) and `World.nodetree->adt` for the Background node's `Strength` (a float socket, unclamped) and `Color` (RGBA, clamped at 0) — the same split and the same socket reader a material uses (`anim/driver/socket.rs`), measured with the lights (`tests/light_driver_truth.rs`, LIGHTDRIVERS fixture)

Blender's three clamp rules ported as measured, not assumed: a float or vector socket takes the value unclamped even where RNA says 0..1, an RGBA socket's component clamps at 0 below and is free above 1, and a `Material` float property clamps to its RNA hard range at both ends. A driver on a **linked** socket is written and never folded into the surface, as Blender's link feeds the shader instead; a muted driver writes nothing. 195 values across 5 frames within 5.4×10⁻⁷ of Blender's evaluated materials (`tests/mat_driver_truth.rs`, MATDRIVERS fixture)
